# DECISIONS.md

1. **Indexes.** `employees`: unique `emp_code` (identity, 409 on duplicate); `(department, emp_code)` for the sorted list; `(department, joined_on)` and `(joined_on)` for headcount (R9). `attendance_logs`: unique `(emp_code, date)` (one record per day, monthly summary, the `$lookup` join); `(date -1, emp_code)` for the list sort and month scans; `(status, date -1, emp_code)` for status filters; `(emp_code, punch_in -1)` for finding the open record at punch-out. I rejected a separate `(date, department)` index: department lives on `employees`, so it would mean copying data into every log and keeping it in sync.
2. **Punch-in race.** Both requests read the employee and compute the same `(emp_code, date)`, then both call `insert_one`. MongoDB's unique index lets exactly one insert succeed; the other raises `DuplicateKeyError`, which I turn into 409. There is no "check then insert" step to race on.
3. **Ties.** `$setWindowFields` with `$rank` gives ties the same rank (1, 2, 2, 4), and `limit` filters on `rank <= limit` afterwards. So both tied employees are returned and the list can be longer than `limit`.
4. **Headcount.** The summary starts from `employees` (joined on or before month end), joins the month's logs with `$lookup`, and `$unwind`s with `preserveNullAndEmptyArrays`. Headcount is the number of distinct `emp_code`s per department, so people with zero logs still count.
5. **100x data.** I'd stop computing monthly/department aggregates on the fly: keep a pre-aggregated daily summary per employee (updated on each punch/correction) and read from that, and use keyset pagination instead of `skip` for the list.
